## 1. 判断の要点

「現行候補を本番採用しない」は支持する。しかし「何も学べていない」「教師ラベルが主因」「単語・文字方式の限界が確定した」という強い説明は支持しない。

保存された新6件について、単語モデルは暫定ラベルに対する全9正負ペアを正しく並べていた。本人の方針承認4件でも順位は分かれる。これは少なくとも「配信元だけで完全に一定のスコアを返す」という説明に対する反証である。ただし少数・選択済みの事例であり、内容を本質的に理解したこと、独立人間精度、未来への汎化を証明しない。[数値][rep-results] [承認来歴][approved]

一方、固定の採否境界では新6件も承認4件も全件保留になる。**自動的に確認件数を減らせた証拠はないが、順位付けまで無価値と決まったわけではない。** 順位が役に立つかは別の利用目的・評価が必要で、今回勝手に製品目的を変更しない。

### 2.1 「AIに関係する」と「AI外電で拾いたい」は別の採点問題

[DESIGN][design] は媒体ごとの編集方針を学ぶ設計であり、普遍的なAI判定器の設計ではない。さらに以下を区別する必要がある。

- **記事自体への編集判断:** 全文や背景知識も含め、AI外電で拾いたいか。
- **入力から判定できる範囲:** モデルに渡すtitle+summaryだけに、その判断を支える情報があるか。

前者が正しい人間判断でも、後者の入力に根拠が十分あるとは限らない。これを単純に「人間ラベルが間違っている」と扱わない。

公開の[gold-review][gold-review]には、AI機構の詳細を述べないGitHubのUI例が人間Rで残っている。また[bootstrap][bootstrap2]にはAI関連ライブラリの小さな修正もRで含まれる。一方、[隔離manifest][quarantine]ではHyperPodの管理・権限等が「新しいML機能・研究ではない」という理由で暫定Nとされ、その後、政策境界として隔離されている。[新6件manifest][probe]の冷却記事も、RSSでAIの使い方を説明しないことを暫定Nの根拠としている。

**確認できるのは、境界の決め方が一つの明示的なルールへ十分落ちていないこと。個々のラベルの矛盾を証明したわけではない。** 「AIツールの利用・運用に直接役立つものは含めるが、一般UIは含めない」等の一貫した方針はありうる。どれを採るかは本人の編集判断である。

Googleの一部概要はcaption、他sourceでは空概要もある。[bootstrap][bootstrap2]と[gold-review][gold-review]の実入力で確認できる。ただし「短い／空だから必ず情報不足」ではなく、titleに十分な情報がある場合もある。長さだけで一律に除外しない。

**提案:** 将来の注釈では、採否R/Nと別に `evidence_status`（入力内に根拠あり／背景に依存／情報不足／方針未決）を記録する。これは教師の品質・観測可能性のmetadataであり、モデルの第三学習クラスにしない。モデルの`uncertain`はスコア帯であり、人間の「情報不足」と同義ではない。旧goldを遡って書き換えない。

### 2.2 URL検査は実装されているが、OOF側の入力で消えている

[representation_probe.py][rep-code]では、OOF用の`ordered`を `id/source/title/summary/label` のみで作って`grouped_splits()`へ渡している。`source_url`が落ちる。[evaluation_design.py][groups-code]が使う[support.py][support-code]のURL照合は、この入力では使えない。

固定コミットの2ファイルをconnector経由で取得し、ローカルへ複写したbytesのGit blob SHAを照合した。

| ファイル | Git blob SHA |
|---|---|
| support.py | `fd3a88c2f8a7158528b8fbc9dc08cd8d58283ea9` |
| evaluation_design.py | `03af183cb1bb2272ba57322e8fbb299934ea847f` |

その原関数に、同一URL・別source・別id・異なる見出しと概要の合成2行を渡すと、**URLを保持した入力では1群、OOFと同じ5フィールドへ絞ると2群**になった。同じ文章ならURLなしでも1群になる対照と、時間境界を跨ぐ同一群をpurgeする対照も確認した。

これは検査経路の欠落の実証である。元59件の全URL・原文を突き合わせていないため、**実際にtrain/testへ同じ記事が漏れたとは報告しない。** 新6件を保護集合と照合する別経路は元のmetadataを持つので、この欠落だけでその重複検査まで無効とは言えない。

修正案は、特徴量入力と同一記事判定用metadataを分離し、群構築ではURLを保持すること。モデル特徴へURLを追加する提案ではない。またURLだけで近似記事を全部検出できるわけでもない。今回コード修正はしていない。

### 2.4 「採用根拠なし」は適切。ただし原因の断定はできない

[C10の局所比較][causal]は、教師上で既存境界を越えられるようになっても既知goldの確信採用3件中正解1件だった、と報告している。これを採用しない判断は妥当。ただしC10が一律に悪い、正則化が無関係、OOVが唯一の原因とは言えない。

ゼロ特徴入力のP(R)は元C1で.736642、C10で.839170との記録がある。C10では特徴の寄与がなくても.80を越えるため、「高スコア＝AIの内容を捉えた」とは限らない。これは記録されたモデルの診断で、通常の記事が全部ゼロ特徴になるという意味ではない。

**しきい値調整自体は不正ではない。** [公式の説明][sk-threshold]でも、学習したスコアと、実際に行動を決める境界は分けて扱う。問題は既知goldや承認4件を見ながら調整して、その同じ集合で成功を主張すること。将来、独立した開発用データで境界を決め、別の未見評価で測る余地は残る。今回その探索・校正は実行も採用もしない。[校正の説明][sk-calibration]

## 4. 次に行う最小検証は一つ: 6件・3境界の入力同条件ラベル監査

### 何を区別するか

**H1: 編集方針が決まりきっていない。** 同じ入力でも「AI利用そのもの」か「AI周辺の開発・運用まで」かで答えが変わる。

**H2: 入力に採否の根拠が不足する。** 方針を決めても、title+summaryだけでは判断できず、製品背景や全文を補っている。

**H3: この6件については教師の判断が明確。** 共通方針・同一入力でも元ラベルに疑義が少なければ、少なくともこの標本でラベル不整合を主因とする説明は弱まる。ただし全59件の教師品質やモデル側の原因を確定しない。

これは**教師・方針・入力の監査**であって、未知記事への精度を測る模試ではない。全体の再学習やしきい値探索を始めるより先に、採点問題が一致しているかを確かめる。

### 候補は3source・各2件

原入力のhash一致確認後に、この6件のID・役割・順序を固定する。以下は題材の説明であり原RSSの転載ではない。

| source | 境界を確かめる1件 | 比較のための1件 |
|---|---|---|
| GitHub | 評価計画に残るCopilot CLIの端末ASCII/UI実装 | 新6件の`NEW_GH02`、coding agentの指示・環境設定 |
| AWS | 隔離済みHyperPodの管理・統治例 | bootstrap `95f314d9…`、MoE強化学習の処理性能改善 |
| Microsoft | 新6件の`NEW_MS01`、データセンター冷却 | 新6件の`NEW_MS02`、AIの企業活用 |

GitHub境界とAWS境界の参照は[評価計画][eval-plan]、Microsoft等のID/hashは[probe manifest][probe]、AWS比較例は[bootstrap/01][bootstrap1]から特定できる。新たな大量取得は不要。既知の承認MS01～MS04とgoldを再質問しない。R/Nを半々にすることも要求しない。監査で全件Rになれば、それも方針に関する結果である。

### 手順・固定条件

1. **助手が準備:** 元作業環境で、モデルに渡したものと同じ6件のtitle+summary（切り詰め等も同一）をmanifestと照合。本文を復元できない行を別記事や新要約で埋めない。完全一致を確認できなければ該当境界の監査は未実施として止める。元教師・goldは変更しない。
2. **同じ情報で先に読む:** 提案ラベル・理由・モデルスコア・ペア対応を隠し、順序をシャッフルした6件の原入力を読む。source/URLの追加表示もしないが、本文中の企業名は消さない。完全なsource-blindとは称さない。既知候補なので「人間にも未見の独立test」とも称さない。
3. **二軸で記録:** 「拾う／拾わない／情報不足／方針未決」と、入力内の根拠箇所または必要な背景情報を記す。情報不足をNへ押し込まない。既存モデルのUとは別の監査metadataとして保存する。
4. **本人が決めるのは主に3境界:** 一般UI、AI/ML専用基盤の一般管理、AI利用の説明がない物理設備を、どこまで編集対象にするか。助手の答えへの一括同意ではなく、最初の読みの後に方針を短く確定する。方針で判断が変わる行だけ理由付き追記し、初回判断は消さない。
5. **採点の勝敗を作らず一巡で停止:** モデルのfit、C変更、threshold変更、元gold修正はしない。6件の初回判断と方針確認後の差、情報不足件数、元の暫定判断との食い違いを記録する。既知モデルスコアをあとで参考に並べても、教師や選択済み事例を含むため独立精度とは呼ばない。

### 事前に決める分岐・停止条件

| 観測 | 支持する説明 | 次の扱い |
|---|---|---|
| 方針を明確にすると同じ入力の採否が変わる | 方針の不定性が少なくともその事例に存在する | 該当カテゴリの注釈規則を文書化。旧goldは保存し、新版の扱いを別判断 |
| 方針確認後も原入力だけでは情報不足 | 入力の不足／背景依存がその事例に存在する | 入力改善または人手確認として扱う。曖昧例をNで増やさない |
| 6件が同一方針で明確に読め、元判断も維持される | この標本でラベル問題を主因とする説明は弱まる | 未見評価を用意してから、表現・学習・境界のどこを比較するか別判断 |
| 原入力がhash一致せず、方針も決まらない | 検証条件が未成立 | 成功／失敗を採点せず停止。モデル探索へ逃げない |

人間作業の上限は6件の短い原入力と3境界。59件全部の再採点は求めない。助手は照合、重複整理、原入力と解釈の分離、結果表を担当できる。**既存データにラベルを上書きする許可は、この提案に含めない。**

### source・群・時間の扱い

同source内で2件を比べるが、独立な3sourceすべてへの汎化評価ではない。URL・同一文章・版違い・同一事象の群を保持し、6件間の重複も確認する。学習済み／隔離／既知probeという元の役割を記録し、役割を「未見」に塗り替えない。今回は学習しないため、train/testを新設したとは報告しない。

publication日時を保持する。この6件は過去事例の監査であり、future holdoutではない。将来に汎化を測る段階では、既存[評価計画][eval-plan]のcutoff `2026-10-09T00:00:00Z`、7日embargo、評価開始 `2026-10-16T00:00:00Z`を使うか別途固定する。同一記事・同一事象の群が境界を跨ぐ場合のpurgeが必要。7日という長さ自体が独立性の保証ではない。source留置評価は該当sourceを学習から外す別実験であり、既存59件モデルの採点だけで代用しない。

将来の性能評価では、対象sourceごとの自然な連続流と、意図的な正負対比の評価を分ける。少数balanced事例のprecisionを実運用precisionとして使わない。今回、その追加取得・学習・予約・自動化は提案の実行範囲に含めない。

## 6. 初心者向けに一言

今回は「生徒にもっと問題を解かせる」前に、**先生の採点基準と、生徒に渡した問題文が同じ条件になっているか**を確かめる段階だ。

AIの仕組みを説明した記事だけを拾うのか、AIツールの使い方や運用の記事も拾うのか。人間は背景を知っていても、短いRSSにはその手掛かりがないこともある。ここが揃わないまま学習回数を増やすと、点数が変わった理由を判断しにくい。

6件の監査は大きな精度保証を作るものではない。**何を学ばせるか、何を入力だけで判断できるかを切り分け、次の実験の問いを正しくする**ための最小の一手である。
